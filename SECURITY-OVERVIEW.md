# Обзор концепции безопасности

Краткая карта связей. Полные формулировки: [требования](SECURITY_REQUIREMENTS.md), [модель угроз](THREAT-MODEL.md), [решения](DESIGN-CASE.md).

## Продукт и граница доверия

```text
 Сотрудник                              Пользователь
   1. регистрирует находку                смотрит каталог
   3. одобряет или отклоняет              2. подаёт обращение
      обращение, фиксирует выдачу            со скрытыми признаками вещи
        │                                     │
════════╪═════ граница доверия: клиент ↔ API ═╪════════
        ▼                                     ▼
   Сервер на Go: проверяет личность, роль, владельца,
   состояние и состав ответа
        │
        ▼
   PostgreSQL: пользователи, сессии, находки,
   обращения, выдачи
```

Состояния: находка `доступна` → `зарезервирована` → `выдана`; обращение `на рассмотрении` → `одобрено` → `завершено` или `на рассмотрении` → `отклонено`.

## Угрозы, требования и решения

Высокий приоритет:

```text
T-07 подмена личности или роли    → SR-07 личность и роль определяет сервер, 401
T-01 служебная команда от         → SR-01 служебные операции только
     обычного пользователя                сотруднику, 403
T-02 чтение чужого обращения      → SR-02 чужое обращение не видно, 404
       └───────────────────────┬───────────────────────┘
                               ▼
D-01 серверная сессия: токен → хеш → сессия → роль из БД;
     проверка роли до разбора тела; SQL-фильтр по владельцу


T-05 закрытые признаки в каталоге → SR-05 в ответе только открытые поля
T-06 служебные поля в обращении   → SR-06 лишние поля отклоняются, 400
       └───────────────────────┬───────────────────────┘
                               ▼
D-02 отдельные структуры запроса и ответа;
     неизвестные поля JSON отклоняются
```

Средний приоритет:

```text
T-03 выдача без одобрения         → SR-03 выдача только по одобренному
                                          обращению этой находки, 409
T-04 два одобрения одновременно   → SR-04 одобряется только одно, 409
T-08 сбой посреди выдачи          → SR-08 выдача сохраняется целиком
       └───────────────────────┬───────────────────────┘
                               ▼
D-03 транзакция с блокировкой находки;
     уникальные ограничения в БД


T-09 подбор или утечка паролей    → SR-09 пароли хранятся необратимо,
                                          подбор ограничен, 429
     решение будет принято при реализации входа
```

## Цепочка T-07 → SR-07 → D-01

```text
T-07  клиент без токена или с чужим user_id / ролью Сотрудник;
      сервер верит запросу → действия от чужого имени
  │
  ▼
SR-07 личность и актуальная роль определяются только сервером
      нет, неизвестный или истёкший токен → 401
      user_id и role из запроса ничего не меняют
      смена роли в БД действует со следующего запроса
  │
  ▼
D-01  вход → случайный токен 32 байта → клиенту
      в sessions только SHA-256 хеш, user_id, expires_at = 8 ч
      каждый запрос: хеш → сессия → роль из БД → контекст
      ограничения: запрос к БД на каждый вызов, кража токена
  │
  ▼
Проверка  без токена / случайный / истёкший    → 401
          чужой user_id и роль в запросе       → 403
          сменить роль в БД, тот же токен      → новая роль
```
