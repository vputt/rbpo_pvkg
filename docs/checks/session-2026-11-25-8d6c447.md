## Критерий SR-07: сквозной тест

Тест поднимает настоящий роутер с проверкой сессии и настоящую базу; защищённый обработчик отдаёт личность, которую положила в контекст проверка сессии. Токен получен настоящим входом.

```text
--- PASS: TestRequestIdentityComesFromTheServer (0.68s)
    --- PASS: TestRequestIdentityComesFromTheServer/no_token (0.00s)
    --- PASS: TestRequestIdentityComesFromTheServer/arbitrary_string_as_token (0.00s)
    --- PASS: TestRequestIdentityComesFromTheServer/valid_token (0.00s)
    --- PASS: TestRequestIdentityComesFromTheServer/identity_from_the_request_is_ignored (0.00s)
    --- PASS: TestRequestIdentityComesFromTheServer/role_change_is_seen_by_the_next_request (0.00s)
    --- PASS: TestRequestIdentityComesFromTheServer/expired_session (0.00s)
```

| Случай | Ожидание | Результат |
| --- | --- | --- |
| запрос без токена | `401`, обработчик не вызван | выполнено |
| произвольная строка вместо токена | `401`, до базы запрос не доходит | выполнено |
| действующий токен | `200`, личность - `user_id` владельца сессии и роль `user` | выполнено |
| в теле `{"user_id":999,"role":"staff"}` и в строке запроса `?user_id=999&role=staff` | личность не меняется | выполнено |
| `UPDATE users SET role = 'staff'`, затем запрос **тем же** токеном | роль в контексте - `staff` | выполнено |
| `expires_at` сдвинут в прошлое | `401` | выполнено |

Защищённый обработчик за весь тест вызван ровно три раза - только на трёх разрешённых запросах; это отдельная проверка в конце теста.

## Поиск по коду: откуда берётся личность

Пункт требует убедиться, что `user_id` и `role` не читаются из запроса. Поиск по рабочему коду без тестов:

```text
r.URL / PathValue / FormValue / ParseForm / r.Header.Get
internal/httpapi/middleware.go:24: token, ok := bearerToken(r.Header.Get("Authorization"))
```

Это единственное место, где читается что-либо из заголовков или адреса запроса. Единственный разбираемый контракт тела - `login` и `password` на входе:

```text
internal/httpapi/auth.go:27: Login    string `json:"login"`
internal/httpapi/auth.go:28: Password string `json:"password"`
```

`role` в рабочем коде встречается только в SQL таблицы пользователей, в команде создания учебных записей и в сервисе создания пользователя; `user_id` - только в запросе чтения сессии. Полей `user_id` и `role` ни в одном входном контракте нет, поэтому подставить их в запрос нельзя - что и проверено сквозным тестом.

## Запущенный сервер

```text
GET /health                -> {"status":"ok"}200
GET /ready                 -> {"status":"ready"}200
POST /api/auth/login       -> 200
GET /api/items без токена  -> 404
GET /api/items с токеном   -> 404
```

Открытые маршруты работают без токена. `GET /api/items` отвечает `404`, потому что обработчиков находок ещё нет: маршрут не зарегистрирован, а не открыт. Журнал сервера за всё время - одна строка с адресом прослушивания.

## Ограничения проверки

- Защищённых маршрутов в продукте пока нет, поэтому проверка сессии проверена на тестовом защищённом обработчике через настоящий роутер. Когда появятся обработчики находок и обращений, тот же набор случаев нужно повторить на реальном маршруте - это делает кусок 18.
- Отказы `403` для роли сотрудника и `404` для чужого обращения в этом куске не реализованы и не проверялись: они относятся к шагам будущей проверки D-01, которые закрываются вместе с предметными обработчиками.
- Истёкшие сессии не выбираются условием по времени сервера БД, но из таблицы не удаляются. Накопление истёкших строк на учебном стенде не проверялось.
- Кража действующего токена из границы проверки исключена сознательно: ограничение записано в D-01.
- Токен передаётся по HTTP без шифрования канала - учебный стенд.
