# Модель угроз

## Модель продукта

**Описание потоков:** Клиент отправляет HTTP-запросы на серверное приложение. Сервер аутентифицирует запрос, проверяет права и бизнес-правила, после чего взаимодействует с реляционной базой данных для чтения или изменения состояния находок и обращений.

База данных возвращает записи и результат сохранения серверу; сервер формирует ответ клиенту с учётом его полномочий. Точки входа: регистрация находки, просмотр каталога, подача и просмотр обращения, рассмотрение обращения и подтверждение выдачи. При выдаче изменяются запись о выдаче, состояние находки и связанных обращений. Решение о допустимости каждого действия принимает сервер.

Сервер и БД находятся в зоне ответственности команды. Клиентское окружение и физическая передача вещи находятся вне программной границы продукта. Внешних сетевых интеграций нет.

**Что уже существует:**

- Определены границы продукта, роли, основные сценарии и требования безопасности.
- Реализован минимальный HTTP-сервер на Go с GET /health.
- Подготовлены модель находки и хранилище в памяти с тестами; к HTTP они пока не подключены.

**Что планируется:**

- Реализация операций с находками, обращениями и выдачей.
- Аутентификация, проверка полномочий и защитные механизмы.
- Подключение реляционной БД.

**Существенные допущения:**

- База данных находится в изолированном доверенном окружении и недоступна извне; доступ к ней имеет только серверное приложение.
- Сервер определяет ID пользователя и его роль по данным аутентификации, а не по произвольным полям запроса.

## Границы доверия

| Граница | Что пересекает | Почему требуется проверка |
| --- | --- | --- |
| Внешний клиент - Серверное API | Данные аутентификации, ID находок и обращений, описания, признаки собственности, фильтры, решения и команды выдачи; обратно - разрешённые данные и результаты операций. | Клиентское окружение не контролируется, в том числе у сотрудника. Параметры можно изменить или отправить напрямую через API. Сервер проверяет полномочия, принадлежность обращения, текущее состояние и состав ответа. |

## Значимые объекты и свойства

См. раздел 5 в [PROJECT.md](PROJECT.md). 
Ключевые объекты защиты:

1. **Карточка находки** - закрытые признаки и место хранения не должны раскрываться обычным пользователям; одобрение обращения не меняет их полномочия.
2. **Обращение претендента** - данные должны быть изолированы от других пользователей, а статус не должен изменяться владельцем.
3. **Решение и запись о выдаче** - выдача допустима только по одобренному обращению, одной вещи соответствует не более одного получателя; связанные состояния должны оставаться согласованными.
4. **Учётная запись и роль** - определяют личность пользователя и доступные ему действия; клиент не должен иметь возможности назначить их самостоятельно.

## Угрозы

Связанные требования приведены в [SECURITY_REQUIREMENTS.md](SECURITY_REQUIREMENTS.md). Угрозы описывают возможные нарушения при отсутствии соответствующей проверки. Высокий приоритет означает прямую угрозу закрытым данным или выдаче вещи в основном сценарии; средний - существенные последствия при дополнительных условиях; низкий - ограниченные последствия и редкие условия.

| ID | Сценарий угрозы | Что нарушается | Граница / точка входа | Связанные SR | Приоритет и обоснование |
| --- | --- | --- | --- | --- | --- |
| T-01 | Обычный пользователь напрямую вызывает регистрацию находки, одобрение или отклонение обращения либо подтверждение выдачи; сервер принимает служебную команду без проверки роли. | Полномочия и целостность учёта: ложная карточка, неправомерное решение или отметка о выдаче | Внешний клиент ↔ API / служебные операции | SR-01 | **Высокий**. Доступен через прямой запрос обычного пользователя; знание структуры API не является защитой. Требует проверки служебных полномочий. |
| T-02 | Пользователь А подменяет ID обращения в GET-запросе на ID обращения Б; сервер возвращает запись без проверки владельца. | Конфиденциальность чужих признаков собственности, обстоятельств утраты и решения | Внешний клиент ↔ API / просмотр обращения | SR-02 | **Высокий**. Достаточно одного известного чужого ID. Утечка помогает подготовить ложное обращение; необходима проверка доступа к объекту. |
| T-03 | Сотрудник отправляет команду выдачи без связанного одобренного обращения; сервер проверяет роль, но не состояние обращения, и фиксирует выдачу. | Целостность процесса: вещь учтена как выданная без одобрения | Внешний клиент ↔ API / подтверждение выдачи | SR-03 | **Высокий**. Ошибка порядка действий возможна без злого умысла и затрагивает основную операцию. Требует проверки допустимого перехода состояния. |
| T-04 | Два сотрудника одновременно одобряют разные обращения на одну находку; оба обработчика проверяют отсутствие одобрения до сохранения и принимают оба решения. | Согласованность: два одобренных претендента на одну вещь, предпосылка повторной выдачи | Внешний клиент ↔ API / рассмотрение обращения и запись в БД | SR-04 | **Высокий**. Достаточно двух одновременных запросов, высокая нагрузка не нужна. Влияет на согласованность проверки и изменения данных. |
| T-05 | При GET-запросе публичного каталога сервер возвращает полные объекты БД, включая `private_marks` и `storage_location`. | Конфиденциальность закрытых признаков и места хранения вещи | Внешний клиент ↔ API / ответ каталога | SR-05 | **Высокий**. Штатный запрос раскрывает признаки нескольких вещей и помогает составить ложное обращение; место хранения облегчает хищение. Влияет на состав ответа API. |
| T-06 | Пользователь добавляет в JSON создания обращения поля `"status": "одобрено"` или чужой `user_id`; сервер сохраняет переданные значения вместо начального состояния и текущего пользователя. | Целостность обращения: одобрение появляется без решения сотрудника либо обращение создаётся от чужого имени | Внешний клиент ↔ API / подача обращения | SR-06 | **Высокий**. Пользователь управляет телом запроса и может создать ложное основание для выдачи или подменить автора. Требует разграничения клиентских и серверных полей. |
| T-07 | Клиент обращается к защищённой операции без действительной аутентификации либо передаёт в запросе чужой `user_id` или роль `Сотрудник`; сервер использует эти значения при определении полномочий. | Подлинность пользователя и разграничение доступа: выполнение действий от имени другого пользователя или сотрудника | Внешний клиент ↔ API / вход и любая защищённая операция | SR-07 | **Высокий**. От установленной личности зависят все проверки доступа. Подмена позволяет читать чужие обращения и выполнять служебные операции. |
| T-08 | При подтверждении выдачи из-за сбоя сохраняется только часть изменений: запись о выдаче, состояние находки или состояния связанных обращений. | Согласованность учёта: выданная вещь может остаться доступной, а обращения - незавершёнными; появляется возможность повторной выдачи | Сервер ↔ БД / подтверждение выдачи | SR-08 | **Высокий**. Операция изменяет несколько связанных записей, а частичный результат нарушает основной бизнес-процесс и допускает повторную выдачу. |

## Приоритетный набор

**T-01, T-02, T-04, T-07, T-08**.
*Обоснование:* Эти угрозы затрагивают установление личности, проверку роли и принадлежности данных, а также согласованность одобрения и выдачи. Они влияют на общую обработку защищённых запросов и изменение связанных записей.

T-03, T-05 и T-06 также требуют выполнения связанных требований: выделенный набор не отменяет проверку последовательности выдачи, состава публичного ответа и служебных полей обращения.
