# Проектные решения безопасности

## D-01. Защита от подмены идентификатора
**Контекст:** Злоумышленник может попытаться прочитать чужое обращение, перебирая идентификаторы в URL (`GET /api/claims/{id}`).
**Решение:** Извлечение идентификатора пользователя (`user_id`) происходит исключительно из доверенного контекста авторизации, а не из параметров запроса. В слое доступа к данным поиск выполняется с обязательной фильтрацией по владельцу: `SELECT * FROM claims WHERE id = $1 AND user_id = $2`.
**Обоснование:** Данные из токена криптографически защищены от подмены. Фильтрация на уровне SQL-запроса гарантирует, что чужая запись не будет прочитана из базы и передана в слой бизнес-логики, что исключает человеческий фактор (например, если разработчик забудет проверить владельца уже загруженного объекта).
**Связанные угрозы и требования:** `T-02`, `SR-02`.
**Будущая проверка:** 
- *Условие:* Существует обращение `ID=10`, принадлежащее пользователю А. Аутентифицирован пользователь Б.
- *Действие:* Пользователь Б выполняет запрос `GET /api/claims/10`.
- *Ожидаемый результат:* Сервер возвращает статус `404 Not Found` или `403 Forbidden`, тело ответа не содержит данных обращения `ID=10`.
**Существенные ограничения:** Не выявлены.

## D-03. Защита от манипуляции параметрами
**Контекст:** При создании нового обращения пользователь может попытаться передать в теле запроса скрытые поля (например, `"status": "одобрено"`), чтобы автоматически завладеть вещью без участия сотрудника.
**Решение:** Строгое разделение структур для приема данных и для работы с БД. В HTTP-хендлере используется структура `ClaimCreateRequest`, содержащая только разрешенные для пользовательского ввода поля (`item_id`, `description`). Функция `c.BindJSON()` в Gin привязывает входящий JSON только к этой структуре, автоматически игнорируя любые лишние переданные ключи. Начальный статус `на рассмотрении` жестко задается на уровне бизнес-логики сервера при создании записи.
**Обоснование:** Парсер игнорирует непредусмотренные поля на самом раннем этапе обработки запроса. Бизнес-логика полностью контролирует начальное состояние нового объекта, не доверяя клиенту.
**Связанные угрозы и требования:** `T-06`, `SR-06`.
**Будущая проверка:**
- *Условие:* Пользователь авторизован.
- *Действие:* Пользователь отправляет `POST /api/claims` с телом `{"item_id": 1, "description": "...", "status": "выдана"}`.
- *Ожидаемый результат:* Сервер возвращает `201 Created` или `200 OK`. В базе данных и в теле ответа созданное обращение имеет статус `на рассмотрении`, то есть, сервер проигнорировал поле `status` из запроса.
**Существенные ограничения:** Отсутствуют.
