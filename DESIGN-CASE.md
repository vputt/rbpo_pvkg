# Проектные решения безопасности

## D-01. Серверная сессия и проверка доступа
**Контекст:** Клиент может обратиться без действительной сессии, передать чужой идентификатор обращения или попытаться назначить себе роль сотрудника.

**Решение:** После проверки логина и пароля сервер создаёт непрозрачный случайный токен длиной 32 байта и возвращает его клиенту, клиент передаёт его в заголовке `Authorization: Bearer`. В таблице `sessions` сохраняются только SHA-256 хеш токена, `user_id` и срок действия `expires_at`, равный 8 часам с момента входа. Для защищённого запроса middleware вычисляет хеш переданного токена, находит неистёкшую сессию и загружает актуальную роль пользователя из БД в серверный контекст. Отсутствующий, неизвестный или истёкший токен приводит к `401 Unauthorized`.

Регистрация находки, изменение её состояния, одобрение, отклонение и подтверждение выдачи требуют роли `Сотрудник`, проверка роли выполняется до обработки тела служебного запроса, отказ - `403 Forbidden`. Обращение обычного пользователя выбирается с фильтрацией по владельцу: `SELECT * FROM claims WHERE id = $1 AND user_id = $2`, чужое или отсутствующее обращение - `404 Not Found`. Значения `user_id` и `role` из запроса не определяют личность и полномочия.

**Обоснование:** Источник личности остаётся в серверном контуре, а фильтрация на уровне SQL не позволяет загрузить чужую запись до проверки владельца.

**Рассмотренная альтернатива:** Подписанный JWT с ролью внутри токена позволяет не обращаться к БД при каждом запросе. Но роль в нём фиксируется в момент входа: сотрудник, у которого отозвали роль, сохраняет полномочия до истечения токена, а для досрочного отзыва всё равно нужен серверный список отозванных токенов. Это противоречит критерию SR-07, по которому изменение роли учитывается при следующем запросе. Для одного сервера с одной БД дополнительный запрос к `sessions` - приемлемая цена. Выбор стоит пересмотреть, если появятся несколько сервисов без общей БД или проверка сессии станет узким местом по нагрузке.

**Предположения:** Токен генерируется криптографически стойким генератором `crypto/rand`, не попадает в журналы сервера и передаётся только владельцу. Роли меняются только в БД, через API их изменить нельзя.

**Связанные угрозы и требования:** `T-01`, `T-02`, `T-07`, `SR-01`, `SR-02`, `SR-07`.

**Будущая проверка:**
- *Условие:* Обращение `id=10` принадлежит пользователю А, пользователь Б имеет действующий и истёкший токены, создана учётная запись сотрудника.
- *Действие:* Отдельно выполнить защищённый запрос без токена, с произвольным и истёкшим токенами. С действующим токеном Б вызвать служебную операцию, подставив чужой `user_id` и роль сотрудника, затем запросить обращение А и своё обращение. Отдельно выполнить служебную операцию с токеном сотрудника, отозвать у него роль в БД и повторить ту же операцию с прежним действующим токеном.
- *Ожидаемый результат:* Первые три случая получают `401`, служебная операция от Б - `403`, чужое обращение - `404` без закрытых данных, собственное - `200`. Служебная операция сотрудника до отзыва роли выполняется, после отзыва с тем же токеном получает `403`. Отказы не изменяют находки, обращения, решения или выдачи, переданные клиентом ID и роль не заменяют серверный контекст.

**Существенные ограничения:** Проверка сессии требует обращения к серверному хранилищу для каждого защищённого запроса. Решение не защищает от кражи действующего токена: до истечения срока украденный токен даёт те же права, что и законному пользователю.

## D-02. Раздельные контракты входных и публичных данных

**Контекст:** Пользователь может передать служебные поля обращения, а возврат модели БД в каталог или в сведения об обращении может раскрыть закрытые признаки вещи.

**Решение:** Поля JSON используют snake_case. Для API используются отдельные структуры: `ClaimCreateRequest` содержит только `item_id`, признаки собственности и обстоятельства утраты. При декодировании используется `json.Decoder` с вызовом `DisallowUnknownFields()`, ошибка неизвестного поля приводит к `400 Bad Request` до записи в БД. Автор и состояние `на рассмотрении` назначаются сервером. Публичная структура находки не содержит `private_marks` и `storage_location` и используется во всех ответах обычному пользователю: в каталоге и во вложенном объекте находки при просмотре собственного обращения. Полная структура находки возвращается только сотруднику.

**Обоснование:** Явный список полей не позволяет клиенту изменять серверные данные и исключает случайную публикацию закрытых сведений при расширении модели БД.

**Пересмотр после разбора:** Сначала мы считали, что закрытые признаки могут попасть к пользователю только через каталог, поэтому T-05, SR-05 и публичная структура находки касались только его. Разбор просмотра собственного обращения показал, что это не так. Пользователь подаёт обращение с произвольными признаками на любую доступную находку и запрашивает его; по SR-02 это его обращение, ответ `200`. Если в ответ вложена полная находка, пользователь видит `private_marks` и `storage_location` и подаёт второе обращение с настоящими признаками, которое сотрудник одобрит. Каталог при этом чист, чужие обращения никто не читает, то есть SR-02 и прежний SR-05 выполнены, а вещь может уйти постороннему. Свойство «одобрение не раскрывает пользователю закрытые признаки» было заявлено в паспорте, но в SR-05 попало только для каталога. Поэтому T-05 дополнен сценарием с обращением, SR-05 распространён на все ответы пользователю, публичная структура находки используется и во вложенных объектах, а в будущую проверку добавлен просмотр собственного обращения.

**Связанные угрозы и требования:** `T-05`, `T-06`, `SR-05`, `SR-06`.

**Будущая проверка:**
- *Условие:* В базе есть находка с заполненными `private_marks` и `storage_location`, пользователь авторизован.
- *Действие:* Запросить каталог, отдельно добавить в корректный запрос обращения `status`, чужой `user_id`, `decision` и произвольное неизвестное поле. Затем отправить исходный корректный запрос. Запросить созданное обращение, затем одобрить его от имени сотрудника и запросить ещё раз.
- *Ожидаемый результат:* В каталоге отсутствуют закрытые поля и их значения. Каждый запрос с неизвестным полем получает `400`, обращение не создаётся. Корректный запрос создаёт обращение от имени текущего пользователя в состоянии `на рассмотрении`. В обоих ответах на просмотр обращения вложенная находка не содержит `private_marks` и `storage_location`.

**Существенные ограничения:** При изменении API структуры запросов и ответов необходимо обновлять явно.

## D-03. Транзакционные переходы состояний

**Контекст:** Два сотрудника могут одновременно одобрить разные обращения, а сбой во время выдачи оставит связанные записи в несогласованном состоянии.

**Решение:** Одобрение выполняется в транзакции PostgreSQL с блокировкой находки через `SELECT ... FOR UPDATE`. После получения блокировки сервер проверяет связь обращения с находкой и актуальные состояния `доступна`/`на рассмотрении`, затем переводит находку в `зарезервирована`, а выбранное обращение - в `одобрено`. Частичный уникальный индекс допускает только одно одобренное обращение на находку. Второй запрос одобрения получает `409 Conflict`, его обращение остаётся `на рассмотрении` до выдачи.

При выдаче сервер в одной транзакции блокирует находку и связанные обращения, проверяет `claim.item_id = item.id` и состояния находки `зарезервирована` и обращения `одобрено`. Неверная связь или состояние приводят к отказу без изменений. Успешная операция создаёт запись выдачи, переводит находку в `выдана`, выбранное обращение - в `завершено`, остальные незавершённые - в `отклонено` и фиксирует транзакцию. Уникальное ограничение по `item_id` в таблице выдач запрещает вторую запись, повторная команда получает `409 Conflict` без изменений.

**Обоснование:** Блокировка упорядочивает конкурентные решения, ограничения БД сохраняют инварианты, а транзакция обеспечивает полный результат либо полный откат.

**Связанные угрозы и требования:** `T-03`, `T-04`, `T-08`, `SR-03`, `SR-04`, `SR-08`.

**Будущая проверка:**
- *Конкуренция:* На двух независимых подключениях к БД одновременно одобрить два обращения `на рассмотрении` на одну доступную находку. Успешно проходит один запрос, второй получает `409`, его обращение остаётся `на рассмотрении`. Находка - `зарезервирована`, одобренное обращение только одно.
- *Выдача без основания:* Для обращений `на рассмотрении` и `отклонено`, а также одобренного обращения на другую находку вызвать выдачу. Сервер возвращает `409`, состояния всех записей и число выдач не меняются.
- *Откат:* На отдельном наборе данных сохранить исходные записи, вызвать ошибку после вставки выдачи, но до завершения связанных обновлений и фиксации транзакции. Проверить записи через другое подключение: находка, все обращения и таблица выдач совпадают с исходным состоянием. 
- *Успех и повтор:* Выполнить выдачу без ошибки: находка - `выдана`, выбранное обращение - `завершено`, остальные незавершённые - `отклонено`, запись выдачи одна. Повторить команду: `409`, вторая запись не появляется, состояния прежние.

**Существенные ограничения:** Связанные записи должны блокироваться в одном порядке, отмена одобрения в границу продукта не входит.
