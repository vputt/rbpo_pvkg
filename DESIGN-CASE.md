# Проектные решения безопасности

## D-01. Серверная сессия и проверка доступа
**Контекст:** Клиент может обратиться без действительной сессии, передать чужой идентификатор обращения или попытаться назначить себе роль сотрудника.

**Решение:** После проверки логина и пароля сервер создаёт непрозрачный случайный токен длиной 32 байта и возвращает его клиенту, клиент передаёт его в заголовке `Authorization: Bearer`. В таблице `sessions` сохраняются только SHA-256 хеш токена, `user_id` и срок действия `expires_at`, равный 8 часам с момента входа. Для защищённого запроса middleware вычисляет хеш переданного токена, находит неистёкшую сессию и загружает актуальную роль пользователя из БД в серверный контекст. Отсутствующий, неизвестный или истёкший токен приводит к `401 Unauthorized`.

Регистрация находки, изменение её состояния, одобрение, отклонение и подтверждение выдачи требуют роли `Сотрудник`, проверка роли выполняется до обработки тела служебного запроса, отказ - `403 Forbidden`. Обращение обычного пользователя выбирается с фильтрацией по владельцу: `SELECT * FROM claims WHERE id = $1 AND user_id = $2`, чужое или отсутствующее обращение - `404 Not Found`. Значения `user_id` и `role` из запроса не определяют личность и полномочия.

**Реализация:** Выдача сессии сделана: `POST /api/auth/login` ([internal/httpapi/auth.go](internal/httpapi/auth.go)) проверяет пароль и создаёт сессию через [internal/service/auth.go](internal/service/auth.go) и [internal/storage/postgres/sessions.go](internal/storage/postgres/sessions.go). Токен - 32 байта из `crypto/rand` в записи base64url; в `sessions` сохраняются только его SHA-256, `user_id` и `expires_at`, равный времени входа плюс `PVKG_SESSION_TTL` (по умолчанию 8 часов) и отсчитываемый от времени сервера БД. Проверка сессии сделана middleware [internal/httpapi/middleware.go](internal/httpapi/middleware.go): читает `Authorization: Bearer`, считает SHA-256 переданного токена и одним запросом берёт `user_id` вместе с **актуальной ролью** из таблицы пользователей при условии `expires_at > CURRENT_TIMESTAMP` ([internal/storage/postgres/sessions.go](internal/storage/postgres/sessions.go), [internal/service/sessions.go](internal/service/sessions.go)); личность кладётся в контекст и читается только через `httpapi.IdentityFrom` ([internal/httpapi/identity.go](internal/httpapi/identity.go)). Истёкшие сессии не выбираются условием по времени сервера БД; отдельная чистка таблицы пока не делается. Отсутствующий, неразбираемый, неизвестный и истёкший токен дают `401` с кодом `unauthorized` до вызова обработчика. Защищённые маршруты оборачиваются проверкой в [internal/httpapi/router.go](internal/httpapi/router.go), а без переданной проверки не регистрируются вовсе, то есть забытая проверка не делает маршрут открытым. Отказы `403` для роли сотрудника и `404` для чужого обращения появятся вместе с соответствующими обработчиками.

**Обоснование:** Источник личности остаётся в серверном контуре, а фильтрация на уровне SQL не позволяет загрузить чужую запись до проверки владельца.

**Рассмотренная альтернатива:** Подписанный JWT с ролью внутри токена позволяет не обращаться к БД при каждом запросе. Но роль в нём фиксируется в момент входа: сотрудник, у которого отозвали роль, сохраняет полномочия до истечения токена, а для досрочного отзыва всё равно нужен серверный список отозванных токенов. Это противоречит критерию SR-07, по которому изменение роли учитывается при следующем запросе. Для одного сервера с одной БД дополнительный запрос к `sessions` - приемлемая цена. Выбор стоит пересмотреть, если появятся несколько сервисов без общей БД или проверка сессии станет узким местом по нагрузке.

**Предположения:** Токен генерируется криптографически стойким генератором `crypto/rand`, не попадает в журналы сервера и передаётся только владельцу. Роли меняются только в БД, через API их изменить нельзя.

**Связанные угрозы и требования:** `T-01`, `T-02`, `T-07`, `SR-01`, `SR-02`, `SR-07`.

**Будущая проверка:**
- *Условие:* Обращение `id=10` принадлежит пользователю А, пользователь Б имеет действующий и истёкший токены, создана учётная запись сотрудника.
- *Действие:* Отдельно выполнить защищённый запрос без токена, с произвольным и истёкшим токенами. С действующим токеном Б вызвать служебную операцию, подставив чужой `user_id` и роль сотрудника, затем запросить обращение А и своё обращение. Отдельно выполнить служебную операцию с токеном сотрудника, отозвать у него роль в БД и повторить ту же операцию с прежним действующим токеном.
- *Ожидаемый результат:* Первые три случая получают `401`, служебная операция от Б - `403`, чужое обращение - `404` без закрытых данных, собственное - `200`. Служебная операция сотрудника до отзыва роли выполняется, после отзыва с тем же токеном получает `403`. Отказы не изменяют находки, обращения, решения или выдачи, переданные клиентом ID и роль не заменяют серверный контекст.

**Существенные ограничения:** Проверка сессии требует обращения к серверному хранилищу для каждого защищённого запроса. Решение не защищает от кражи действующего токена: до истечения срока украденный токен даёт те же права, что и законному пользователю.

## D-02. Раздельные контракты входных и публичных данных

**Контекст:** Пользователь может передать служебные поля обращения, а возврат модели БД в каталог или в сведения об обращении может раскрыть закрытые признаки вещи.

**Решение:** Поля JSON используют snake_case. Для API используются отдельные структуры: `ClaimCreateRequest` содержит только `item_id`, признаки собственности и обстоятельства утраты. При декодировании используется `json.Decoder` с вызовом `DisallowUnknownFields()`, ошибка неизвестного поля приводит к `400 Bad Request` до записи в БД. Автор и состояние `на рассмотрении` назначаются сервером. Публичная структура находки не содержит `private_marks` и `storage_location` и используется во всех ответах обычному пользователю: в каталоге и во вложенном объекте находки при просмотре собственного обращения. Полная структура находки возвращается только сотруднику.

**Обоснование:** Явный список полей не позволяет клиенту изменять серверные данные и исключает случайную публикацию закрытых сведений при расширении модели БД.

**Пересмотр после разбора:** Сначала мы считали, что закрытые признаки могут попасть к пользователю только через каталог, поэтому T-05, SR-05 и публичная структура находки касались только его. Разбор просмотра собственного обращения показал, что это не так. Пользователь подаёт обращение с произвольными признаками на любую доступную находку и запрашивает его; по SR-02 это его обращение, ответ `200`. Если в ответ вложена полная находка, пользователь видит `private_marks` и `storage_location` и подаёт второе обращение с настоящими признаками, которое сотрудник одобрит. Каталог при этом чист, чужие обращения никто не читает, то есть SR-02 и прежний SR-05 выполнены, а вещь может уйти постороннему. Свойство «одобрение не раскрывает пользователю закрытые признаки» было заявлено в паспорте, но в SR-05 попало только для каталога. Поэтому T-05 дополнен сценарием с обращением, SR-05 распространён на все ответы пользователю, публичная структура находки используется и во вложенных объектах, а в будущую проверку добавлен просмотр собственного обращения.

**Связанные угрозы и требования:** `T-05`, `T-06`, `SR-05`, `SR-06`.

**Будущая проверка:**
- *Условие:* В базе есть находка с заполненными `private_marks` и `storage_location`, пользователь авторизован.
- *Действие:* Запросить каталог, отдельно добавить в корректный запрос обращения `status`, чужой `user_id`, `decision` и произвольное неизвестное поле. Затем отправить исходный корректный запрос. Запросить созданное обращение, затем одобрить его от имени сотрудника и запросить ещё раз.
- *Ожидаемый результат:* В каталоге отсутствуют закрытые поля и их значения. Каждый запрос с неизвестным полем получает `400`, обращение не создаётся. Корректный запрос создаёт обращение от имени текущего пользователя в состоянии `на рассмотрении`. В обоих ответах на просмотр обращения вложенная находка не содержит `private_marks` и `storage_location`.

**Существенные ограничения:** При изменении API структуры запросов и ответов необходимо обновлять явно.

## D-03. Транзакционные переходы состояний

**Контекст:** Два сотрудника могут одновременно одобрить разные обращения, а сбой во время выдачи оставит связанные записи в несогласованном состоянии.

**Решение:** Одобрение выполняется в транзакции PostgreSQL с блокировкой находки через `SELECT ... FOR UPDATE`. После получения блокировки сервер проверяет связь обращения с находкой и актуальные состояния `доступна`/`на рассмотрении`, затем переводит находку в `зарезервирована`, а выбранное обращение - в `одобрено`. Частичный уникальный индекс допускает только одно одобренное обращение на находку. Второй запрос одобрения получает `409 Conflict`, его обращение остаётся `на рассмотрении` до выдачи.

При выдаче сервер в одной транзакции блокирует находку и связанные обращения, проверяет `claim.item_id = item.id` и состояния находки `зарезервирована` и обращения `одобрено`. Неверная связь или состояние приводят к отказу без изменений. Успешная операция создаёт запись выдачи, переводит находку в `выдана`, выбранное обращение - в `завершено`, остальные незавершённые - в `отклонено` и фиксирует транзакцию. Уникальное ограничение по `item_id` в таблице выдач запрещает вторую запись, повторная команда получает `409 Conflict` без изменений.

Ограничения схемы реализованы в [начальной миграции](migrations/000001_initial_schema.up.sql): частичный уникальный индекс допускает только одно обращение `approved` на находку, а уникальные ограничения `issuances.item_id` и `issuances.claim_id` запрещают повторную выдачу. Транзакции, блокировки строк и перевод конфликтов БД в ответы API будут реализованы вместе с операциями одобрения и выдачи.

**Обоснование:** Блокировка упорядочивает конкурентные решения, ограничения БД сохраняют инварианты, а транзакция обеспечивает полный результат либо полный откат.

**Связанные угрозы и требования:** `T-03`, `T-04`, `T-08`, `SR-03`, `SR-04`, `SR-08`.

**Будущая проверка:**
- *Конкуренция:* На двух независимых подключениях к БД одновременно одобрить два обращения `на рассмотрении` на одну доступную находку. Успешно проходит один запрос, второй получает `409`, его обращение остаётся `на рассмотрении`. Находка - `зарезервирована`, одобренное обращение только одно.
- *Выдача без основания:* Для обращений `на рассмотрении` и `отклонено`, а также одобренного обращения на другую находку вызвать выдачу. Сервер возвращает `409`, состояния всех записей и число выдач не меняются.
- *Откат:* На отдельном наборе данных сохранить исходные записи, вызвать ошибку после вставки выдачи, но до завершения связанных обновлений и фиксации транзакции. Проверить записи через другое подключение: находка, все обращения и таблица выдач совпадают с исходным состоянием. 
- *Успех и повтор:* Выполнить выдачу без ошибки: находка - `выдана`, выбранное обращение - `завершено`, остальные незавершённые - `отклонено`, запись выдачи одна. Повторить команду: `409`, вторая запись не появляется, состояния прежние.

**Существенные ограничения:** Связанные записи должны блокироваться в одном порядке, отмена одобрения в границу продукта не входит.

## D-04. Хранение паролей и ограничение подбора

**Контекст:** Пароли учебных записей хранятся в таблице `users`, а вход доступен любому клиенту без предварительной аутентификации и без ограничения частоты запросов. Угроза T-09 распадается на два разных исхода: восстановление пароля из содержимого БД и подбор пароля через повторные запросы входа, - и каждый закрывается своей мерой.

**Решение:** Пароль не хранится в открытом или обратимом виде: в `users.password_hash` сохраняется результат `bcrypt` со стоимостью 12 (`golang.org/x/crypto/bcrypt`, стоимость задана константой в коде сервиса). Соль генерирует библиотека и помещает её вместе с версией и стоимостью в саму строку хеша, поэтому две записи с одинаковым паролем получают разные значения. Проверка выполняется только через `bcrypt.CompareHashAndPassword`, пароль в открытом виде никуда не сохраняется и не попадает в журналы.

Подбор ограничивается по учётной записи. В `users` для этого есть `failed_login_count` и `locked_until`; порог и срок берутся из конфигурации - `PVKG_LOGIN_MAX_FAILS` (по умолчанию 5) и `PVKG_LOGIN_LOCK_FOR` (по умолчанию 15 минут). Обработчик входа работает так:

- Если `locked_until` в будущем - ответ `429 Too Many Requests` до проверки пароля, в том числе при верном пароле; токен не выдаётся, `failed_login_count` и `locked_until` не меняются, то есть попытки во время блокировки её не продлевают.
- Если `locked_until` в прошлом, блокировка считается снятой: счётчик обнуляется, и у владельца снова есть полный набор попыток.
- Неверный пароль - `401` и увеличение счётчика; при достижении порога тем же оператором выставляется `locked_until` = `CURRENT_TIMESTAMP` + срок блокировки. Чтение записи, сравнение и обновление счётчика выполняются в одной транзакции, иначе параллельные попытки теряют счёт и порог не срабатывает (та же природа, что у T-04).
- Верный пароль - `200`, `failed_login_count` обнуляется, `locked_until` снимается.

Время блокировки записывается и сравнивается по `CURRENT_TIMESTAMP` сервера БД, а не по часам приложения: источник времени для записи и для проверки один и тот же.

Ответ входа не различает неизвестный логин и неверный пароль: в обоих случаях `401` с одинаковым телом `{"error":{"code":"invalid_credentials","message":"неверный логин или пароль"}}`. Чтобы различие не проявлялось через время ответа, для неизвестного логина выполняется сравнение с заготовленным хешем-заглушкой - иначе быстрый ответ сам сообщает, что такого логина нет.

**Реализация:** Решение реализовано полностью. Хранение: стоимость 12 задана константой `service.PasswordCost`, хеширование и проверка - [internal/service/users.go](internal/service/users.go), создание учебных записей - [cmd/seed-users/main.go](cmd/seed-users/main.go). Ограничение подбора: вход читает запись запросом `SELECT … FOR UPDATE` вместе с `CURRENT_TIMESTAMP` сервера БД, сравнивает пароль и обновляет счётчик в одной транзакции - [internal/service/auth.go](internal/service/auth.go), [internal/storage/postgres/users.go](internal/storage/postgres/users.go), [internal/storage/postgres/transaction.go](internal/storage/postgres/transaction.go). Фактические значения: порог 5 попыток из `PVKG_LOGIN_MAX_FAILS`, срок блокировки 15 минут из `PVKG_LOGIN_LOCK_FOR`, при действующей блокировке - `429` с кодом `too_many_attempts` до проверки пароля и без выдачи токена. Одинаковый ответ на неизвестный логин и неверный пароль - `401` с кодом `invalid_credentials`, время выровнено сравнением с хешем-заглушкой, который считается один раз при старте ([internal/httpapi/auth.go](internal/httpapi/auth.go)). Шаги будущей проверки закрыты тестами [users_integration_test.go](internal/storage/postgres/users_integration_test.go) и [lockout_integration_test.go](internal/storage/postgres/lockout_integration_test.go); фактический прогон критерия приёмки - [отчёт о проверке](docs/checks/lockout-2026-11-25-50bb3cc.md).

**Обоснование:** Медленный хеш с солью нужен именно для пароля: его выбирает человек, поэтому при утечке содержимого БД пароль подбирают перебором по словарю. `bcrypt` со стоимостью 12 делает одну проверку дорогой, а соль в каждом хеше исключает заранее посчитанные таблицы и совпадение хешей у одинаковых паролей. Быстрый `SHA-256`, которым по D-01 хешируются токены сессий, для паролей не подходит: токен - 32 случайных байта, его не угадывают, а пароль угадывают, и быстрый хеш только ускоряет перебор.

Блокировка привязана к учётной записи, а не к адресу клиента, потому что защищаемое утверждение SR-09 сформулировано про попытки входа в одну запись, а запись - серверная сущность под нашим контролем. Адрес клиента в границу доверия не входит и не идентифицирует атакующего: за одним адресом может работать вся сеть организации (тогда блокировка задевает законных пользователей), а запросы с меняющихся адресов обходят ограничение, не затрагивая счётчик.

**Рассмотренная альтернатива:** `argon2id` (`golang.org/x/crypto/argon2`) требователен к памяти и поэтому устойчивее к перебору на GPU, тогда как у `bcrypt` расход памяти фиксированный и небольшой. Для учебного продукта выбран `bcrypt`: у него один параметр - стоимость, она записана в самом хеше вместе с солью, а проверка делается готовой функцией. У `argon2id` в `x/crypto` нужно самостоятельно выбрать и обосновать три параметра под оборудование и самостоятельно же закодировать параметры и соль рядом с хешем, то есть сопровождение и миграция хешей становятся нашим кодом. Выбор стоит пересмотреть, если продукт выйдет за пределы учебного стенда с настоящими паролями пользователей или если устойчивость к перебору на GPU станет заявленным требованием.

Вторым вариантом ограничения подбора рассматривался общий лимит запросов входа по адресу клиента. Он отклонён по причинам выше: не отделяет атакующего от законных пользователей за тем же адресом, обходится сменой адреса и при этом требует отдельного хранилища счётчиков, которого у продукта нет.

**Предположения:** Проверяемые. Стоимость 12 даёт на машинах команды не меньше 0,1 с на одно сравнение: на Apple M4 (macOS, Go 1.27.0) измерено 0,18 с, бенчмарк `BenchmarkVerifyPassword` в куске 5. Ожидавшиеся 0,2 с не подтвердились, порог повышения стоимости - сравнение быстрее 0,1 с - не достигнут; измерение повторяется на машине второго участника. Строка `bcrypt` - 60 символов ASCII и помещается в `password_hash` типа `TEXT`. Пароли учебных записей задаются через окружение и не попадают ни в историю репозитория, ни в журналы. Время на сервере БД не переводится назад вручную. Других путей создания пользователя, кроме пути с хешированием, у продукта нет: в миграциях нет вставки пароля в открытом виде.

**Связанные угрозы и требования:** `T-09`, `SR-09`.

**Будущая проверка:**
- *Хранение.* Условие: созданы две учебные записи с одинаковым паролем. Действие: прочитать `password_hash` обеих записей напрямую из БД и проверить верный и неверный пароль через функцию сравнения. Ожидаемый результат: ни одно значение не равно паролю, значения различаются между собой, оба начинаются с `$2a$12$`; верный пароль проходит проверку, неверный - нет.
- *Подбор.* Условие: учебная запись с известным паролем, `failed_login_count = 0`, `locked_until` пусто, порог 5 и срок 15 минут. Действие: пять раз подряд отправить вход с неверным паролем, затем шестой раз - с верным. Ожидаемый результат: первые пять попыток - `401` с одинаковым телом, шестая - `429` без токена; в записи `failed_login_count = 5`, `locked_until` на 15 минут вперёд, сессия не создана.
- *Снятие блокировки.* Условие: та же запись под блокировкой. Действие: сдвинуть `locked_until` в прошлое и отправить вход с верным паролем. Ожидаемый результат: `200`, токен выдан, `failed_login_count = 0`, `locked_until` пусто.
- *Блокировка не продлевается.* Условие: запись под блокировкой, значения `locked_until` и `failed_login_count` зафиксированы. Действие: отправить ещё три запроса входа с неверным паролем. Ожидаемый результат: `429` на каждый, оба значения в записи не изменились.
- *Неизвестный логин.* Условие: логина `nobody` в БД нет. Действие: отправить вход с этим логином. Ожидаемый результат: `401` с тем же телом, что при неверном пароле; новых записей в `users` нет.

**Существенные ограничения:** Блокировка по учётной записи позволяет внешнему клиенту намеренно лишить входа законного владельца: достаточно пяти неверных попыток, чтобы вход был недоступен 15 минут. Для учебного продукта это принято осознанно - отказ ограничен по времени, данные при нём не теряются, а попытки во время блокировки её не продлевают.

После снятия блокировки счётчик обнуляется, поэтому решение ограничивает скорость подбора (пять попыток за 15 минут на запись, порядка 480 попыток в сутки), но не останавливает его: слабый пароль остаётся уязвимым, поэтому пароли учебных записей задаются длинными и случайными.

Подбор, распределённый по многим записям - один вероятный пароль на список логинов, - не ограничивается: счётчик у каждой записи свой, общего лимита попыток входа у продукта нет.

Ответ `429` сам раскрывает, что такая запись существует и находится под блокировкой, тогда как для неизвестного логина отдаётся `401`. Это следствие критерия приёмки SR-09, который требует именно `429`; тело ответа при этом остаётся без подробностей.

Стоимость хеширования записана в самом хеше: после повышения константы ранее созданные записи продолжают проверяться со старой стоимостью, пока их хеш не перезапишут. Перехеширование при успешном входе в границу продукта пока не входит. `bcrypt` учитывает только первые 72 байта пароля - остаток более длинного пароля на проверку не влияет.

Медленный хеш означает расход процессорного времени на каждую попытку входа, и поток неверных попыток по разным логинам нагружает сервер; блокировка по записи такой нагрузки не ограничивает.
