# Проектные решения безопасности

## D-01. Защита от подмены идентификатора
**Контекст:** Клиент может обратиться без действительной сессии, передать чужой идентификатор обращения или попытаться назначить себе роль сотрудника.
**Решение:** Идентификатор пользователя и его роль извлекаются только из доверенного контекста авторизации. Служебные операции требуют роли `Сотрудник`, а обращение пользователя выбирается с фильтрацией по владельцу: `SELECT * FROM claims WHERE id = $1 AND user_id = $2`. Значения `user_id` и `role` из запроса не определяют полномочия.
**Обоснование:** Источник личности остаётся в серверном контуре, а фильтрация на уровне SQL не позволяет загрузить чужую запись до проверки владельца.
**Связанные угрозы и требования:** `T-01`, `T-02`, `T-07`, `SR-01`, `SR-02`, `SR-07`.
**Будущая проверка:**
- *Условие:* Существует обращение `ID=10` пользователя А; пользователь Б имеет действительную сессию.
- *Действие:* Выполнить защищённый запрос без сессии, затем от имени Б передать роль сотрудника и запросить `GET /api/claims/10`.
- *Ожидаемый результат:* Запрос без сессии получает `401`, служебная операция и чтение чужого обращения — `403` или `404`; данные и состояние не изменяются.
**Существенные ограничения:** Проверка сессии требует обращения к серверному хранилищу для каждого защищённого запроса.

## D-02. Раздельные контракты входных и публичных данных
**Контекст:** Пользователь может передать служебные поля обращения, а возврат модели БД в каталог может раскрыть закрытые признаки вещи.
**Решение:** Для API используются отдельные структуры. `ClaimCreateRequest` содержит только `item_id`, признаки собственности и обстоятельства утраты; неизвестные поля отклоняются с `400 Bad Request`. Автор и состояние `на рассмотрении` назначаются сервером. Публичная структура находки не содержит закрытых признаков и места хранения.
**Обоснование:** Явный список полей не позволяет клиенту изменять серверные данные и исключает случайную публикацию закрытых сведений при расширении модели БД.
**Связанные угрозы и требования:** `T-05`, `T-06`, `SR-05`, `SR-06`.
**Будущая проверка:**
- *Условие:* В базе есть находка с закрытыми признаками; пользователь авторизован.
- *Действие:* Запросить каталог и отправить обращение с полями `status`, чужим `user_id` и решением.
- *Ожидаемый результат:* В каталоге нет закрытых данных; запрос со служебными полями получает `400`, обращение не создаётся. Корректный запрос создаёт обращение от имени текущего пользователя в состоянии `на рассмотрении`.
**Существенные ограничения:** При изменении API структуры запросов и ответов необходимо обновлять явно.

## D-03. Транзакционные переходы состояний
**Контекст:** Два сотрудника могут одновременно одобрить разные обращения, а сбой во время выдачи — оставить связанные записи в несогласованном состоянии.
**Решение:** Одобрение выполняется в транзакции PostgreSQL с блокировкой находки через `SELECT ... FOR UPDATE`; находка переводится из `доступна` в `зарезервирована`. Частичный уникальный индекс допускает только одно одобренное обращение на находку. Выдача одной транзакцией создаёт запись выдачи и обновляет находку и все связанные обращения. Уникальное ограничение по `item_id` запрещает повторную выдачу; повторная команда возвращает `409 Conflict`.
**Обоснование:** Блокировка упорядочивает конкурентные решения, ограничения БД сохраняют инварианты, а транзакция обеспечивает полный результат либо полный откат.
**Связанные угрозы и требования:** `T-03`, `T-04`, `T-08`, `SR-03`, `SR-04`, `SR-08`.
**Будущая проверка:**
- *Условие:* Для доступной находки существуют два обращения `на рассмотрении`.
- *Действие:* Одновременно одобрить оба обращения, затем проверить выдачу, сбой перед фиксацией транзакции и повтор команды.
- *Ожидаемый результат:* Одобряется одно обращение; при сбое изменения откатываются; успешная выдача согласованно обновляет все записи, повторная команда не создаёт вторую выдачу.
**Существенные ограничения:** Связанные записи должны блокироваться в одном порядке; отмена одобрения в границу продукта не входит.
