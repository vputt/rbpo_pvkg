# Требования безопасности

Сценарии нарушения требований описаны в [модели угроз](THREAT-MODEL.md).

| ID | Требование | Критерий приёмки | Связанные угрозы |
| --- | --- | --- | --- |
| SR-01 | Система разрешает регистрацию находок и изменение их состояния только пользователям с ролью «Сотрудник» (v5.0.0-8.2.1). | При попытке обычного пользователя выполнить запрос на создание карточки вещи или изменение её состояния, сервер отклоняет действие (возвращает 403 Forbidden), а состояние базы данных остаётся неизменным. | T-01 |
| SR-02 | Система запрещает пользователю доступ к данным чужих обращений, защищая от подмены идентификатора (IDOR) (v5.0.0-8.2.2). | При попытке пользователя A запросить данные обращения пользователя B по прямому идентификатору, сервер возвращает ошибку (например, 403 или 404), чужие данные в ответе отсутствуют. | T-02 |
| SR-03 | Система соблюдает строгую последовательность логики: выдача вещи невозможна без предварительного наличия одобренного обращения (v5.0.0-2.3.1). | При попытке сотрудника зафиксировать выдачу находки, для которой нет связанного обращения в статусе `одобрено`, действие отклоняется, статус вещи не меняется. | T-03 |
| SR-04 | Система защищает от состояния гонки и двойного использования ресурса, не позволяя одобрить выдачу одной вещи нескольким претендентам (v5.0.0-2.3.4). | При одновременной попытке одобрить два разных обращения на одну и ту же находку, успешно завершается только одно действие. Второе обращение отклоняется сервером, повторная выдача не происходит. | T-04 |
| SR-05 | Система возвращает в публичный каталог только разрешённое подмножество данных, скрывая закрытые признаки вещи (v5.0.0-15.3.1). | При запросе пользователем каталога находок в статусе `доступна`, в теле ответа сервера строго отсутствуют поля с закрытыми отличительными признаками, даже если они есть в базе данных. | T-05 |
| SR-06 | При создании обращения система определяет автора по аутентифицированному пользователю, устанавливает состояние `на рассмотрении` и не принимает служебные поля из запроса (v5.0.0-15.3.3). | Пользователь А передаёт в запросе `"status": "одобрено"`, `userId` пользователя Б или поле решения. Сервер игнорирует эти значения и создаёт обращение от имени пользователя А в состоянии `на рассмотрении`, без решения сотрудника. | T-06 |
| SR-07 | Система выполняет защищённые операции только для аутентифицированного пользователя и определяет его ID и роль на стороне сервера. | Запрос к защищённой операции без действительных данных аутентификации получает `401 Unauthorized`, данные не возвращаются и состояние не изменяется. Переданные в запросе `userId` и `role` не меняют личность и полномочия пользователя. | T-07 |
| SR-08 | Система сохраняет результат выдачи согласованно: запись о выдаче, состояние находки `выдана`, состояние одобренного обращения `завершено` и состояния остальных незавершённых обращений `отклонено`. | При успешной выдаче сохраняются все перечисленные изменения. При искусственном сбое между изменениями после восстановления остаётся либо исходное состояние, либо полный результат выдачи; частично сохранённого результата нет. | T-08 |
